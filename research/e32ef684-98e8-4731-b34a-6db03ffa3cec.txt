## 2. Prompt structure â€” the important part

### 2.1 The mechanic that explains everything

> "Stitch reads each prompt as a fresh description of the whole screen rather than as an edit to the previous one, so loose wording leaves it room to reinterpret everything." â€” [AIToolsay](https://aitoolsay.com/blog/google-stitch-prompt-guide/)

Every prompt-writing rule below follows from this. Stitch is not applying a diff; it is re-deriving the screen. Anything you leave unstated is up for reinvention, and anything you bundle into one request increases the surface area it will rebuild.

### 2.2 The three official frameworks (they agree)

**Google's `llms.txt` â€” the 3-Layer Vibe Structure:**

1. **Anatomy (Structure)** â€” the physical layout ("split-screen dashboard," "bento grid")
2. **Vibe (Aesthetic)** â€” the emotional language ("glassmorphism," "neo-brutalism," "clean SaaS")
3. **Content (Context)** â€” the data payload ("real estate listings," "crypto tickers")

**Google's `generate-design` skill â€” the generation template.** This is the highest-signal artifact I found; it is literally the format Google tells its own agents to emit:

```markdown
[Overall purpose and user intent of the page]

**PLATFORM:** [Web/Mobile], [Desktop/Mobile]-first

**PAGE STRUCTURE:**
1. **Header:** [Description of navigation and branding]
2. **Hero Section:** [Headline, subtext, and primary CTA]
3. **Primary Content Area:** [Detailed component breakdown]
4. **Footer:** [Links and copyright information]
```

**Google's `enhance-prompt` skill â€” the variant used when no project design system exists.** Same skeleton, with the tokens inlined as an explicit block:

```markdown
[One-line description of the page purpose and vibe]

**DESIGN SYSTEM (REQUIRED):**
- Platform: [Web/Mobile], [Desktop/Mobile]-first
- Theme: [Light/Dark], [style descriptors]
- Background: [Color description] (#hex)
- Primary Accent: [Color description] (#hex) for [role]
- Text Primary: [Color description] (#hex)

**Page Structure:**
1. **[Section]:** [Description]
2. **[Section]:** [Description]
```

### 2.3 Long or short? Both â€” but for different jobs

There is a clean split that most guides muddle:

- **Generation prompts should be long and structured.** Google's own examples run 150â€“250 words with numbered sections. The Zoom-Out-Zoom-In example below is ~200 words and produces markedly better output than a one-liner.
- **Edit prompts should be short and singular.** One change, one named component. Google's tip list says it outright: "Keep edits focused: one edit at a time is often better than a long list of changes."

**Hard ceiling: roughly 5,000 characters.** Fiska Syela, who shipped four apps entirely in Stitch, reports that "for prompts over ~5,000 characters, the AI consistently starts omitting components or ignoring specific requirements." No official number exists; treat 5k as the practical wall and stay well under it.

**One screen or a whole app per prompt?** Google's guide says start high-level for brainstorming, then "drill down on details screen by screen." In practice: **2â€“4 screens per generation prompt**, then one screen per refinement prompt. Feeding 15 screens at once causes Stitch to drop quality or silently skip screens.

### 2.4 Where to put colors, fonts, and pixel values â€” the rule everyone gets wrong

Google's `generate-design` skill carries an explicit caution:

> **Do NOT include hex codes, font names, color palettes, roundness values, or any design system tokens in a generation prompt.** These are applied at the project level by the manage-design-system skill and will conflict if duplicated. (For **edit** prompts, hex codes are acceptable for precise color adjustments.)

So the correct division of labor is:

| Concern | Where it goes |
|---|---|
| Colors, fonts, radii, spacing scale | DESIGN.md / project design system â€” **once** |
| Layout, sections, components, copy | Generation prompt â€” **per screen** |
| Exact hex for a targeted fix | Edit prompt â€” **allowed and encouraged** |

This directly contradicts a lot of community advice (Cengiz DÃ¶nmez puts hex codes in every prompt and it works for him â€” because he has no project design system configured). Both work; mixing them is what breaks. If you have a design system, keep styling out of generation prompts. If you don't, inline it consistently in every single prompt.

**Does it respect exact values?** Mostly yes, with caveats. Hex codes are the single highest-leverage specificity gain â€” "Say 'coral' and you'll get a different shade every time. Say `#E8725A` and you'll get the exact same one." Font names work (`Public Sans`, `Space Grotesk`, `Source Serif 4`, `Fraunces`). Pixel values work in DESIGN.md tokens and in edit prompts (`16px border radius`, `reduce horizontal padding by 8px`). But one deep-dive review lists "color accuracy: struggles to implement specific color requests accurately" as a known weakness, and Stitch's internal `designTheme` object stores font and roundness as coarse enums (`INTER`, `ROUND_EIGHT`) plus a single `customColor` â€” which suggests the project-level theme is lower-resolution than your prompt.

### 2.5 Iterative refinement

Stitch maintains conversational context, so follow-ups build on the previous result. The discipline:

- **Name the location, then the change.** Google's three-part edit anatomy: *Location* ("Change the primary button in the hero section...") â†’ *Visuals* ("...to a darker blue (#004080) and add a subtle shadow.") â†’ *Structure* ("Add a secondary button next to the primary one with the text 'Learn More'.")
- **One major change per prompt.** Bundling is the #1 documented cause of Stitch rebuilding a screen you liked.
- **Multi-select for global changes.** Shift+Click screens on the canvas, then issue one prompt. This is the workhorse move for consistency.
- **Prefer editing over regenerating.** Google's skill: "Do NOT re-generate from scratch unless the fundamental layout is wrong."
- **Variants for exploration.** The Variants feature generates 1â€“5 alternatives with a `creativeRange` of `REFINE` / `EXPLORE` / `REIMAGINE`, scoped to `LAYOUT`, `COLOR_SCHEME`, `IMAGES`, `TEXT_FONT`, or `TEXT_CONTENT`. Prajwal Tomar's framing: "You're curating, not just accepting."

There is **no region-based or direct-manipulation editing**. You cannot drag, nudge, or align. Text, colors, font family, and corner radius are editable through the Design System panel; everything else requires re-prompting.

### 2.7 Getting real copy instead of lorem ipsum

Stitch does not produce lorem ipsum by default â€” it produces something worse: confident AI filler. Fabricated metrics ("99.98% UPTIME SLA", "124ms AVG. RESPONSE"), generic names ("John Doe", "Acme", "Nexus"), and clichÃ©s ("Elevate", "Seamless", "Unleash", "Next-Gen").

Three fixes, in order of effectiveness:

1. **Write the copy in the prompt, verbatim and quoted.** Google's own gold-standard example does exactly this: `Headline: "Elevate Every Beat." Sub-headline: "Track, analyze, and crush your fitness goals with Pulse." Primary CTA button: "Get Started".`
2. **Ban the filler explicitly in DESIGN.md.** The `taste-design` skill encodes: "Never generate metrics, performance numbers, uptime percentages, response times, or any data the user did not explicitly provide... If real data is not available, use clear placeholder labels like `[metric]` instead of making up numbers."
3. **Use the `copywriting` skill** from the stitch-skills repo, which replaces placeholder copy with marketing-quality writing fitted to the product.

### 2.8 Phrasings that reliably work

- Numbered `**Page Structure:**` sections â€” the single highest-yield formatting choice
- Named components from the keyword list: navigation bar, hero section, card grid, bottom sheet, segmented control, horizontal scrolling chips, floating action button, skeleton loader, toast notification
- `"On the [screen], add a [component] to the [region]."`
- `"Change the [named element] in the [named section] to [specific value]."`
- `"Switch all product copy and button text to [language]."` â€” Google's documented localization phrasing
- `"Standardize the headers and tabs across all these to match Screen 1."` â€” recommended by a Google staffer on the forum for multi-select
- `"You only generated 1 screen. Please generate all 3 screens I described."` â€” recovery for skipped screens; usually works on the second attempt
- `"Review this DESIGN.md for inconsistencies, accessibility issues, and missing edge cases."` â€” free design review
- Interaction language ("hover states, animations, click behavior") rather than visual styling, per Google's tips

### 2.9 Phrasings and patterns that fail

- **"Do not change X" rules.** Widely reported as unreliable. A forum thread titled ["Stitch is becoming almost unusable for real design work"](https://discuss.ai.google.dev/t/stitch-is-becoming-almost-unusable-for-real-design-work/170296) leads with exactly this: detailed instructions with clear do-not-change rules get ignored, unrelated areas change.
- **Bundled changes.** "Redesign the homepage, add search, improve colors, change navigation, move buttons, add icons, and update the layout" â€” guaranteed rebuild.
- **Unnamed targets.** "Change the button" instead of "the primary button on the sign-up form."
- **Abstract adjectives alone.** "Make it look high-end."
- **Prompts over ~5,000 characters.** Components start disappearing.

> ```

**Why it works:** explicit **primary / secondary / tertiary** hierarchy tells Stitch what to make visually loudest â€” most prompts omit this entirely. The negative constraints ("no heavy gradients or decorative elements") suppress default AI slop. And stating the output expectation frames the fidelity level.

His follow-up, which is a model of a good edit prompt â€” short, two related changes, one of them a standard:

> ```
> Change background to dark gray, ensure you follow WCAG 2.1
> ```

### 3.3 Multi-screen opener (Abhi Chatterjee, [Design Systems Collective](https://www.designsystemscollective.com/the-design-md-workflow-how-google-stitch-claude-code-quietly-changed-the-design-to-code-handoff-c4213f97ed8f))

> ```
> Design a mobile app called Cadence - a calm, minimal habit tracker.
> Target audience: people who find Streaks and Habitica overwhelming and want something quiet.
> Generate 3 screens:
> 1. Home - list of today's routines, time of day, calm tick-off interaction
> 2. Routine detail - single habit with a 7-day history, streak count subtle, no flames

Generated all three screens in ~40 seconds. **Why it works:** positions the product *against* named competitors, which gives Gemini a concrete latent-space anchor; bans specific failure modes by name ("no flames," "no confetti," "no celebrations"); and the reference aesthetic line does more work than any adjective list could.

### 3.5 The incremental dashboard sequence (AIToolsay case study)

This is the best documented example of *sequencing*. A factory operator dashboard, built in three prompts after a single bundled prompt destroyed the layout.

Prompt 1:

> ```
> Create a web dashboard to display a task list for factory operators.
> Each task should appear as two rows.
> First row: Task title, Operator name, Sector, Machine, Deadline, and Status.
> Second row: Task description that spans the full width below the first row.
> Use a clean, modern style suitable for fullscreen display in an industrial setting.
> ```

Prompt 2:

> ```
> Above the task table, add a horizontal row of filter dropdowns for:
> Task title, Operator name, Sector, Machine, Deadline, Status.
> The filters should be evenly spaced and styled minimally.
> ```

Prompt 3:

> ```
> Move the page title to the left side of the screen, aligned with the task table.
> Add a small gear icon to the top-right corner of the screen for admin settings access.
> ```

**Why it works:** each prompt has exactly one objective and specifies position relative to an existing named element ("above the task table," "aligned with the task table"). The author's failed attempts all combined filters + title alignment, or filters + icons, in a single request.

### 3.6 Google's own single-line examples (from the official Prompt Guide)

These are worth quoting because they show how much a short prompt can carry when the words are chosen well:

> `"Product detail page for a Japandi-styled tea store. Sells herbal teas, ceramics. Neutral, minimal colors, black buttons. Soft, elegant font."`

> `"Product detail page for Japanese workwear-inspired men's athletic apparel. Dark, minimal design, dark blue primary color. Minimal clothing pictures, natural fabrics, not gaudy."`

> `"Music player page for 'Suburban Legends.' Album art is a macro, zoomed-in photo of ocean water. Page background/imagery should reflect this."`

> `"An app for marathon runners to engage with a community, find partners, get training advice, and find races near them."`

**Why they work:** each names a concrete aesthetic movement or cultural reference (Japandi, Japanese workwear), states the product category, and includes one or two negative constraints ("not gaudy," "minimal clothing pictures"). The music player example is the clearest demonstration of directing imagery â€” it describes a specific photograph and tells Stitch to propagate it into the background.

### 3.7 Targeted edits (Google's documented patterns)

> `"On the homepage, add a search bar to the header."`

> `"Change the primary call-to-action button on the login screen to be larger and use the brand's primary blue color."`

> `"On 'Team' page, image of 'Dr. Carter (Lead Dentist)': update her lab coat to black."`

> `"Update theme to light orange. Ensure all images and illustrative icons match this new color scheme."`

> `"Make all buttons have fully rounded corners."` / `"Give input fields a 2px solid black border."`

That fourth one is a pattern most people miss: when you change a theme, **explicitly tell Stitch to propagate it into generated imagery and icons**, or they'll stay on the old palette.

## 4. Multi-screen products â€” a 15-screen portal

### 4.1 Is there a "theme" concept? Yes, three overlapping ones

1. **`designTheme`** â€” the project-level object, visible in the Design System panel. Fields: `colorMode` (LIGHT/DARK), `font`, `roundness`, `customColor`, `saturation`. Coarse but global.
2. **DESIGN.md** â€” the real design system. YAML front matter with machine-readable tokens (`colors`, `typography`, `rounded`, `spacing`, `components`) plus a markdown body of human-readable rationale organized into fixed-order sections: Overview â†’ Colors â†’ Typography â†’ Layout â†’ Elevation & Depth â†’ Shapes â†’ Components â†’ Do's and Don'ts. Stitch auto-generates one from your canvas and keeps it in sync bidirectionally. It's portable across Claude Code, Cursor, v0 â€” anything that reads a file.
3. **`apply_design_system`** â€” applies a saved design system to existing screens, available via MCP.

The DESIGN.md token schema, condensed:

```yaml
---
name: Heritage
colors:
  primary: "#1A1C1E"
  tertiary: "#B8422E"
typography:
  h1: { fontFamily: Public Sans, fontSize: 3rem }
  body-md: { fontFamily: Public Sans, fontSize: 1rem }
rounded: { sm: 4px, md: 8px }
spacing: { sm: 8px, md: 16px }
components:
  button-primary:
    backgroundColor: "{colors.tertiary}"
    textColor: "{colors.on-tertiary}"
    rounded: "{rounded.sm}"
---
```

Validate it with `npx @google/design.md lint DESIGN.md` â€” it checks broken token references, WCAG AA contrast on every component color pair, orphaned tokens, and section ordering. On Windows use the `designmd` alias (`npx -p @google/design.md designmd lint DESIGN.md`) because the `.md` suffix collides with the Markdown file association.

### 4.2 The recommended workflow for ~15 screens

This synthesizes the two best-documented multi-screen runs (Cengiz's 16 screens in 2 hours; Abhi's Cadence project) plus the forum answer from a Google staffer.

**Phase 0 â€” plan outside Stitch.** Use a chat model to produce the screen inventory, the components on each screen, and copy-paste-ready Stitch prompts grouped into batches. Cengiz's three questions verbatim: *"What screens does this app need? Give me a complete list."* â†’ *"What components go on each screen? Be detailed."* â†’ *"Break these into groups of 3â€“4 and write a copy-paste-ready Stitch prompt for each group."* This step triples throughput and stops you from burning credits on exploration.

**Phase 1 â€” lock the design system before screen two.** Generate one hero screen, read the auto-generated DESIGN.md carefully, edit it directly (top-down editing is recommended for beginners â€” change `Accent (sage): #8AA890` to `Accent (clay): #B5715F`, save, and Stitch re-renders every screen). MindStudio's warning: *"Making sweeping changes mid-project on a per-screen basis breaks the visual coherence that makes Stitch's multi-page output valuable."*

**Phase 2 â€” generate in batches of 2â€“4.** Never more. Five is the technical ceiling; 2â€“4 is the quality ceiling. If Stitch skips one, say so explicitly and it usually complies on retry.

**Phase 3 â€” the multi-select normalization pass.** Shift+Click every screen, then run the theme prompt from Â§3.4. The Google staffer's alternative phrasing is even simpler and worth trying first: *"Standardize the headers and tabs across all these to match Screen 1."*

**Phase 4 â€” targeted per-screen fixes.** One change per prompt, always naming the component.

**Phase 5 â€” prototype and export.** Link screens, hit Play, walk the flow. Then export â€” and if the Experimental/Pro Figma-export limitation still holds, do the final theme pass in Standard mode before exporting.

### 4.3 Consistency rules

- **Edit the system, not the screens.** "If the change applies to more than one screen, edit the file, not the canvas."
- **Think in color *roles*, not hex values.** Define a Primary role for ink and a Neutral role for canvas. Swap the role definition once and it ripples everywhere. (Fiska Syela)
- **Screenshot every working state.** There is no reliable undo.
- **Keep scope contained.** "It's not the right tool for a sprawling product with hundreds of different page types â€” but for a clean, single-purpose app, it absolutely does the job." A 15-screen government portal is comfortably inside that envelope.
- **Ask Stitch to audit its own system:** *"Review this DESIGN.md for inconsistencies, accessibility issues, and missing edge cases."*
- **Watch the nav bar specifically.** It's the most commonly reported drift point, even in five-star reviews.

### 4.4 The `stitch-loop` pattern (for programmatic runs)

Google ships a skill for exactly the 15-screen problem. It uses a "baton" file, `.stitch/next-prompt.md`, holding one page's prompt with YAML frontmatter. Each iteration reads the baton, consults `.stitch/SITE.md` (vision, sitemap, roadmap) and `.stitch/DESIGN.md`, generates one page, integrates it, updates the sitemap, and writes the next baton. Its listed pitfalls are the same failure modes by another name: forgetting to include the design system block in the prompt, recreating an existing page, leaving `href="#"` placeholders. Note that this path currently depends on `edit_screens`, which has the persistence bug â€” generation works, programmatic editing does not.

## 5. Non-English content, accessibility, responsive output

### 5.1 Bilingual and non-Latin scripts

**What's documented.** Google's only official localization guidance is one line: `"Switch all product copy and button text to Spanish."` The `authoring-stitch-prompts` community skill lists language conversion as a supported revision directive ("switch to Spanish", "German version", "convert to French").

**What the evidence actually says about non-Latin scripts.** Thinner and less encouraging:

- A [detailed Japanese-support analysis](https://book.st-hakky.com/en/data-science/google-stitch-japanese-support-2025-ui-prompt) found that prompt input accepts Japanese, but **generated UI text still contains a lot of English** unless language is specified explicitly and repeatedly. Partial language switching is possible but limited. It also flags a design consequence people forget: **character count and line-height change with script**, and your layout must absorb it.
- The Stitch UI itself is only partially localized. A [forum thread from a Hebrew speaker](https://discuss.ai.google.dev/t/deep-feedback-on-google-stitch-ui-ai-trust-issues-advanced-canvas-management-and-full-functional-preview-requests/172927) reports some elements translating and others staying English, "creating a confusing and inconsistent user experience."
- An Indian-language walkthrough of Stitch lists **"English only: it currently supports only English prompts; Hindi and other language support may come later"** as a limitation.
- **RTL works but must be requested explicitly.** A worked Urdu example shows adding `"right-to-left (RTL) layout for Urdu script"` to the prompt, after which the generated JSX correctly used `text-right rtl` and rendered Urdu strings. The same writeup suggests declaring `direction: "rtl"` as a constraint.

**Practical recommendation for Devanagari/Hindi.** I found no first-party statement either way, so treat this as unverified and test early. Specifically:

1. Name the font: **Noto Sans Devanagari** (or another Devanagari-capable family). Stitch respects font names, and the default stacks will not render Devanagari well.
2. Supply the Hindi strings **verbatim in the prompt**, in Devanagari. Do not ask Stitch to translate â€” machine-translated government terminology is exactly where it will embarrass you, and it demonstrably leaves English fragments behind.
3. Design the layout for **~20â€“30% more vertical space** in Hindi. Devanagari's above- and below-baseline marks need more leading than Latin at the same size.
4. If you need a language toggle, write it into the prompt literally: `language toggle showing "English | à¤¹à¤¿à¤¨à¥à¤¦à¥€"`.
5. Generate the English screens first, get the layout right, *then* run a bilingual pass on the multi-select â€” layout debugging in a script Stitch is weak at is the hard way round.

### 5.2 Accessibility

**What's built in.** As of July 2026 there's an **Accessibility Audit** action: select a screen â†’ Generate â†’ Accessibility Audit, and Stitch produces a report. The DESIGN.md linter enforces a `contrast-ratio` rule flagging any component `backgroundColor`/`textColor` pair below WCAG AA 4.5:1, and Google's DESIGN.md announcement frames this as a headline benefit: agents "can validate their choices against WCAG accessibility rules."

**What's not.** Multiple sources are blunt that AI-generated output does not reliably meet WCAG. One analysis: "Color contrast ratios, screen reader compatibility, keyboard navigation patterns, and other accessibility requirements are not consistently addressed... For organizations with legal accessibility obligations, this creates a significant gap that requires manual review and remediation." Another notes accessibility attributes as one of the things that "need a developer's attention before anything goes to production."

**What to do.** Put WCAG in the prompt (`"ensure you follow WCAG 2.1"` demonstrably changes output), encode contrast and 44px tap targets as rules in DESIGN.md, lint the file, run the built-in audit, and then verify independently. Third-party MCP servers ([stitch-pro-mcp](https://github.com/luciferdono/stitch-pro-mcp), auto-stitch-mcp) add axe-core-backed WCAG 2.1 AA audits with auto-fix for contrast, ARIA, semantics, touch targets, and the `lang` attribute â€” relevant if you're going through an agent anyway. For a government portal with statutory accessibility obligations, treat Stitch output as a visual draft and audit the real implementation.

### 5.3 Responsive and mobile-first

Pick **App or Web at project creation** â€” this is not a cosmetic setting. The canvas takes the right aspect ratio and components are sized accordingly. Programmatically, `deviceType` accepts `MOBILE`, `DESKTOP`, or `TABLET`. Google's own prompt template puts `**PLATFORM:** [Web/Mobile], [Desktop/Mobile]-first` on its own line, above the page structure.

Two things to know: Stitch is **noticeably stronger at mobile than web**, and responsive breakpoints are on the documented list of things exported code tends to skip. The `taste-design` skill encodes the responsive rules worth stealing into your own DESIGN.md verbatim â€” all multi-column layouts collapse to single column below 768px with no exceptions; horizontal overflow on mobile is a critical failure; headlines scale via `clamp()`; body text minimum 16px; all interactive elements minimum 44px; `min-h-[100dvh]` never `h-screen` because of the iOS Safari jump.

## 6. The rules, condensed

1. Stitch re-derives the whole screen on every prompt. Structure and specificity are load-bearing, and omission is an invitation to reinvent.
2. Generation prompts: long and structured, numbered `**Page Structure:**` sections, under ~5,000 characters. Edit prompts: short, one change, name the component and its parent section.
3. Put colors, fonts, radii, and spacing in DESIGN.md â€” not in generation prompts. Hex codes in edit prompts are fine and encouraged.
4. Establish the design system before the second screen. Edit the system, not the screens.
5. 2â€“4 screens per generation prompt. Five is the ceiling; quality degrades before you reach it.
6. Shift+Click all screens and run one theme-normalization prompt. This is the highest-leverage action available.
7. Use professional component nouns from Google's keyword list. "Card grid," not "list of things."
8. Anchor the aesthetic to something physical and named â€” Japandi, Neoclassical, "closer to Linear than Duolingo" â€” not to adjectives like "premium."
9. Write your real copy verbatim in the prompt. Ban invented statistics and names explicitly in DESIGN.md.
10. State negative constraints. "No gradients, no confetti, no purple" works better than hoping.
11. "Do not change X" is unreliable. Design your workflow so nothing you care about is in scope for the current prompt.
12. Screenshot every state you like. There is no reliable undo.
13. Expect to hand-fix dense tables, complex forms, responsive breakpoints, and accessibility. Stitch is a first draft for a coding agent, not a finisher.
